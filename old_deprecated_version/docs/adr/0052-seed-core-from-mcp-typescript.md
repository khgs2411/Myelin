# Seed the V2 core from the existing MCP TypeScript, not the Python query code

A large part of the core logic already exists as self-contained TypeScript in the detached `mcp/src/`: `query-planner.ts`, `query-engine.ts`, `wiki-state.ts`, `fs.ts`, and `inbox.ts` import only each other and Node `fs`/`path` — no MCP SDK, server object, or `contracts.ts` coupling. The V2 core adapts these modules into `src/` rather than re-porting the Python in `agents/query/`. This is how ADR 0048 (core owns query) is realized in practice: the logic moves into core, and the detached MCP later calls core via the CLI/JSON contract.

The TypeScript query path is deterministic — it scores wiki pages from `state/` metadata (`page-metadata.json`, `tag-index.json`, `alias-index.json`, `relationships.json`, `ranking-snapshot.json`) and returns page references. The Python path adds two LLM stages (router, synthesizer). V2 keeps the deterministic TypeScript routing as the query base and treats the LLM router/synthesizer as **optional** stages layered on through the provider abstraction (ADR 0051), so `memory query` works deterministically and only spends tokens when synthesis is requested. The Python query is reference-only.

`wiki-state.ts` (`projectMap`, `listWikiProjects`, `listBrainPages`, `findBrainPages`) backs the `status` walking-skeleton (Task 4). `inbox.ts` (atomic gap-note write + schema) is adapted into core (Task 9); `auto-update.ts`'s lockfile-and-spawn stays an ingest concern and spawns `project ingest` in V2. The TypeScript and Python readers already use identical `state/` file shapes, so adapting the TypeScript requires no data-shape change.
