# Product Integration Roadmap

This is the reusable sequence for adding ClassKit capabilities to a product website while keeping product presentation in the website and product authority behind the SDK and backend.

The canonical execution checklist is [`docs/shared/product_implementation_roadmap.md`](../target-repo/docs/shared/product_implementation_roadmap.md). Product teams may keep a local status copy, but should preserve its dependency order and treat the shared document as the source of truth.

## Non-negotiable boundary

The integration path is `product website -> @class-kit/react -> class-kit-* Edge Functions -> class_kit schema`. A product site owns brand, routes, layout, copy, and interaction design. It does not own ClassKit table access, RPC calls, Edge Function action names, product resolution, authorization policy, or membership/registration rules. Those details are deliberately hidden by `@class-kit/react` and enforced by the backend. [`docs/getting-started.md`](../target-repo/docs/getting-started.md) and [`docs/product-shape.md`](../target-repo/docs/product-shape.md) define this split.

Use one product-local client, created with `createClassKitClient(import.meta.env, { authStorageKey })`, and wrap every ClassKit-powered route with `ProductProvider`. Product context provides product identity, auth policy, current access state, session, and UI capabilities; it is a UI input, not an authorization substitute. The backend remains the final authority. See [`docs/sdk/client-sdk.md`](../target-repo/docs/sdk/client-sdk.md).

## Ordered implementation path

1. **Preflight and product setup.** Verify the product key, site URL and allowed origins, local origin support, Supabase Auth redirect allow-list, ClassKit-managed OAuth redirects, intended auth mode and providers, an available manager, and CI access to the private SDK repository. Install a tagged SDK release (not a raw commit); the documented form is `git+ssh://git@github.com/khgs2411/class-kit-sdk.git#v0.1.18`.
2. **SDK boundary and app shell.** Add the single client and `ProductProvider`, use a product-specific browser auth storage key, define route-level product-context loading and configuration-error states, and ensure no application code reaches for a Supabase client to access ClassKit directly. `VITE_CLASS_KIT_LOCAL_PRODUCT_KEY` is only a localhost disambiguation hint; production product identity is resolved by the backend from the request origin and path-aware site URL.
3. **Route and information architecture.** Establish distinct public discovery, account/authentication, and manager areas before deep feature work. Static marketing material remains visibly separate from ClassKit-managed class inventory and schedules. Capabilities can hide manager navigation, but must not be used as the authorization check.
4. **Authentication, account, and access.** Render password and Google affordances from product context's policy flags. Open products may expose signup; invite-only products must not imply that authentication grants product membership. Use product-managed OAuth redirects rather than frontend redirect configuration. Customer self-service profile reads and writes use `client.profile.*`; manager APIs do not belong in account/onboarding screens.
5. **Manager workspace foundation.** Build a protected operational workspace with consistent loading, error, empty, denied, and refresh states. All manager operations go through `client.management.*`, and manager-only data remains outside customer-safe view models.
6. **Class inventory management.** Let managers create, edit, publish, draft, cancel, and inspect concrete classes before relying on public discovery. Class lifecycle commands are explicit. Customer pages consume only customer-safe `client.classes.*` responses.
7. **Templates and schedules.** Add reusable templates and schedule rules when recurring operations need them. A schedule is a manager-side source rule that generates concrete classes; customers discover and register for generated concrete classes, never schedules.
8. **Public discovery and registration.** Replace mock class content with `client.classes.list/get`, then add `register` and `cancelRegistration`. Preserve the intended class through sign-in, distinguish pending from approved registration, and present backend outcomes such as capacity, cutoff, access, and membership requirements in product-owned language.
9. **Pending registration review.** Where approval is used, add the manager-side pending queue and explicit approve/reject actions. Pending totals must remain separate from approved registrations, and customer self-service continues to use `classes.*`.
10. **Users, roles, and permissions.** Add product-scoped user/role administration only when needed. Supabase identity is global, while ClassKit membership, roles, and permissions are product-scoped. Customer metadata/property edits use `profile.update`; manager edits use the appropriate management methods and should intentionally account for their metadata semantics.
11. **Membership operations.** Add membership types, grants, inspection, and ledger visibility in a dedicated manager workspace when the product uses memberships. Use `setForUser` for “make this user have this membership,” `upgrade` only for rank-based upgrades, and `adjustStock` for balance corrections. Payment and entitlement rules remain ClassKit-owned.
12. **Documents, directed entry, and change requests.** Add public published documents and acceptance recording where required; acceptances snapshot the current document version, so critical flows must not trust cached document text alone. Resolve durable signup links through `signupLinks.resolve` rather than duplicating link-target semantics. Product managers submit change requests through `management.changeRequests.*`; private attachments, admin handling, and external PM integrations such as Trello remain backend/admin concerns.
13. **Attendance and session lifecycle.** After class inventory and registrations exist, managers can start a session, operate an approved roster, record attendance or supported walk-ins/trials, and complete the session. Attendance does not implicitly approve a pending registration.
14. **Product quality and release hardening.** Add localization, accessible controls/dialogs/selected states, responsive manager flows, focused mutation feedback, and safe reconciliation. Then lazy-load route and manager weight where supported, configure the private SDK deploy key for static-host CI, confirm production origins and redirects, and run the product build, typecheck, lint, and smoke checks.

The source roadmap labels both responsiveness/accessibility and performance/deployment hardening as “Phase 16”; they are consecutive final stages, not parallel prerequisites. Treat the latter as the final release gate.

## Scope and completion rule

Not every product needs every operational slice. Static content, payments, analytics, imported rosters, custom landing-page previews, and additional locales are product-specific additions; none justify bypassing the SDK or moving ClassKit business rules into website code.

An integration is complete for its chosen scope only when the relevant UI states, SDK calls, loading/error/empty states, and product-level verification are complete. The minimum final gate is a tagged SDK dependency, `ProductProvider` coverage, product-context-driven auth/access/navigation, configured redirects and origins, public/customer APIs under `classes.*`, manager APIs under `management.*`, and a successful production dependency install and build. The full checklist in [`docs/shared/product_implementation_roadmap.md`](../target-repo/docs/shared/product_implementation_roadmap.md) is the verification reference.
