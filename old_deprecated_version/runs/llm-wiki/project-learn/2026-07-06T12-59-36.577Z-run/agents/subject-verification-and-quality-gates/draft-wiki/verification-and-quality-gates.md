# Verification And Quality Gates

Verification in Myelin combines ordinary Bun/TypeScript checks, schema-context validation, fail-closed retrieval behavior, and Project Memory publication gates. The strongest current contract is deterministic around runtime safety and artifact shape; rendered documentation usefulness is partly implemented in legacy structured-curator validators but is not yet enforced by the active agent-authored Project Memory path.

## Test And Typecheck Surface

The root package is a Bun/TypeScript CLI. `package.json` exposes `bun run typecheck` as `tsc --noEmit`, and normal test execution uses Bun's test runner over `tests/` (`package.json:8-10`). The test tree mirrors the runtime boundaries: `tests/commands/` covers CLI command behavior, `tests/runtime/` covers repository-safe runtime helpers, `tests/schema/` and `tests/commands/schema.test.ts` cover schema generation/checking, `tests/query/` covers Session and Project Memory query responses, `tests/memory/` covers SQLite, embeddings, retrieval indexes, and Session Memory storage, and `tests/project/` covers Project Memory packets, curator validation, rendered-quality contracts, draft promotion, source consumption, and create/maintenance agent flows.

Regression expectations are behavior-focused. For example, `tests/commands/schema.test.ts` verifies that `schema check` is read-only, `schema build --dry-run` previews without writing state, and invalid authored schema rules fail before writing `projects/<key>/state/schema-context.json`. Query regressions in `tests/query/project-memory-query-service.test.ts` verify that Project Memory vector hits are hydrated from current canonical markdown, stale section hashes do not return inline content, and missing sections return degraded references instead of stale answers. Project Memory regressions include `tests/project/project-memory-create-contract-regression.test.ts`, which rejects old role-shaped create output as shallow, and `tests/project/project-memory-rendered-quality.test.ts`, which rejects thin sections and repeated boilerplate.

## Schema Validation

Schema validation is implemented in `src/schema/compiler.ts` and `src/schema/validators.ts`. `checkSchema` finds the project, loads global schema inputs, validates any existing `projects/<key>/state/schema-context.json` with the Zod schema, and reports stale input hashes with a "run schema build" error instead of silently accepting drift (`src/schema/compiler.ts:43-62`). `buildSchemaContext` recompiles from `schema/global.md` plus sorted JSON rule files when hashes change, supports dry-run without writes, and avoids rewriting already-current context (`src/schema/compiler.ts:65-87`).

The compiled context preserves required CLI vocabulary and provenance requirements. `compileContext` emits command names including `project learn`, `memory query`, `schema check`, and `schema build`, and provenance requirements including file-path line evidence, commit pointers, source snippets, and inference labels (`src/schema/compiler.ts:30-41`, `src/schema/compiler.ts:132-157`). Rule schemas in `src/schema/validators.ts` require non-empty lists for source classification, memory scopes, page taxonomy, and schema-context fields; `memoryScopesRuleSchema` also rejects active/deferred scope keys that are not declared in `scopes`.

## Query Fail-Closed Behavior

The public query facade is intentionally degraded rather than exception-leaky. `queryMemory` catches configuration, database, provider, branch, and service errors and returns a `QueryResponse` with `confidence: 0`, `memory_scope: "none"`, empty matches, `degraded: true`, and `degraded_reason` populated (`src/query/engine.ts:20-45`, `src/query/engine.ts:56-69`).

Project Memory query is stricter about not laundering stale index rows into answers. `queryProjectMemory` degrades when sqlite-vec is unavailable, when no Project Memory rows are indexed, or when only pending rows exist and the operator needs `myelin memory index project` (`src/query/project-memory-query-service.ts:80-97`). Vector hits are hydrated back through current markdown sections. If the canonical section is missing, its hash changed, or it is too large to inline, the result becomes a reference-only citation instead of inline content; stale or missing markdown marks the whole Project Memory query degraded (`src/query/project-memory-query-service.ts:161-209`, `src/query/project-memory-query-service.ts:245-301`).

## Structured Curator Quality Gates

The older structured Project Memory curator validator contains the strongest rendered-content contract. `validateCuratorOutput` blocks malformed envelopes, schema-version mismatches, project-key/mode mismatches, packet-ref mismatches, and invalid `quality_diagnostics` before proposal-specific validation (`src/project/project-memory-curator-validator.ts:45-89`). Create-mode drafts require proposal and page evidence refs, a create evidence-map artifact, safe wiki targets, direct line-precise repo citations, supported answer domains, required topics, representative questions, inspected surfaces, concrete apply payloads, and a publication minimum (`src/project/project-memory-curator-validator.ts:92-263`). Maintenance proposals are bounded to 25 items and block non-trusted content quality before canonical writes (`src/project/project-memory-curator-validator.ts:266-318`).

Rendered quality is computed from the markdown that would be published, not from curator intent. `PROJECT_MEMORY_ANSWER_DOMAINS` requires coverage for product/memory model, storage/retrieval, command workflows, curation/apply lifecycle, evidence/provenance/candidates, and current roadmap/decisions (`src/project/project-memory-quality-contract.ts:14-24`). `evaluateProjectMemoryQuality` marks create output shallow when a domain is missing, has no rendered sections, has no repo citation coverage, or has less than 300 non-whitespace body characters (`src/project/project-memory-quality-contract.ts:63-98`). `evaluateRenderedProjectMemoryQuality` renders page drafts, extracts markdown sections, counts `- Repo:` citations, checks answerability terms such as `state/memory.db`, `project learn`, `memory query`, `candidate`, `runtime inbox`, `ROADMAP`, and `ADR`, and flags shallow or repeated boilerplate sections (`src/project/project-memory-rendered-quality.ts:17-58`, `src/project/project-memory-rendered-quality.ts:60-155`).

## Active Project Memory Publication Gates

The active `project learn` implementation now uses agent-authored draft wiki promotion rather than the structured curator-output apply path for create/maintenance runs. Create mode runs a planner file-authoring agent, normalizes and validates `reports/documentation-subject-manifest.json`, requires `draft-wiki/index.md`, requires one markdown file per manifest subject, runs subject writers with one retry, and fails the create result if any subject writer reports non-completion (`src/project/project-memory-agent-create-service.ts:80-124`, `src/project/project-memory-agent-create-service.ts:162-249`). Maintenance mode copies the base wiki, requires `reports/documentation-maintenance-report.json`, validates report status and dispositions, requires every pending project candidate/handoff to receive exactly one disposition, and turns report dispositions into source-consumption records (`src/project/project-memory-agent-maintenance-service.ts:112-181`, `src/project/project-memory-agent-maintenance-service.ts:192-230`).

Draft promotion is staged and journaled. `promoteDraftWiki` lists markdown files from the draft wiki, requires `index.md`, writes Project Memory state and source-consumption state, and delegates actual promotion to `ProjectMemoryMarkdownApplier` (`src/project/project-memory-draft-promotion.ts:24-63`, `src/project/project-memory-draft-promotion.ts:85-103`). The applier writes staged files and a `project-memory-apply-journal.json` before promotion, records expected hashes, blocks recovery when apply artifacts are missing, blocks promotion if canonical files changed before promotion, and blocks recovery when already-promoted canonical files drift from observed hashes (`src/project/project-memory-markdown-applier.ts:87-164`, `src/project/project-memory-markdown-applier.ts:330-424`, `src/project/project-memory-markdown-applier.ts:663-704`).

After promotion, `ProjectMemoryCuratorService` runs source-consumption reconciliation and the retrieval lifecycle. Terminal run artifacts include `input-packet.json`, `curator-validation.json`, `curator-run-result.json`, `summary.md`, optional apply journal/result/changeset, retrieval artifacts, subject reports, maintenance report, and file-authoring run refs (`src/project/project-memory-curator-service.ts:330-494`). Retrieval readiness is updated separately from content state: completed retrieval becomes `ready`, pending retrieval becomes `pending` (`src/project/project-memory-curator-service.ts:330-371`).

## Current Quality Gap

There is an unresolved contract mismatch. The roadmap says rendered markdown quality, answer-domain coverage, answerability checks, and independent usefulness critique are the intended Project Memory quality bar, and the structured-validator code implements much of that contract. But the active agent-authored path records run results with `content_quality_status: "trusted"` while persisted `project-memory.json` state explicitly says `content_quality.status: "not_evaluated"` with reason `agent_authored_documentation_has_no_schema_quality_gate` (`src/project/project-memory-curator-service.ts:457-494`, `src/project/project-memory-curator-service.ts:517-574`). Future work should treat agent-authored Project Memory as shape-validated and promotion-safe, not deterministically usefulness-validated, until the rendered-quality or usefulness-critique gate is wired into the active path.

## Practical Verification Checklist

For runtime changes, run the focused Bun test file for the touched surface, then broader `bun test` when behavior crosses command, memory, query, or Project Memory boundaries. For type-level or public contract changes, run `bun run typecheck`. For schema-context changes, run `myelin schema check <project>` or the matching command tests, and use `schema build --dry-run` when checking generated context without writes. For Project Memory changes, verify both the mechanical path and the trust boundary: run the relevant `tests/project/*` suites, confirm apply journals and changesets are produced before terminal journal state, and do not describe agent-authored documentation as content-quality validated unless the active path produced an explicit quality artifact.
