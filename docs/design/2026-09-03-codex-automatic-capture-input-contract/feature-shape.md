# Codex Automatic-Capture Input Contract — Feature Shape

> Historical source record. This unit is retired from active design.

This unit records the verified native inputs available to a future Codex
capture adapter and the accepted event granularity for captured evidence. It
does not define the shared captured-activity seam, install hooks, or implement
capture.

Design issue status: [Open Design Issues](design-issues.md).

## Verified Provider Surface

The locally installed `codex-cli 0.153.0` reports stable hook support. Its
embedded command-hook schemas expose these lifecycle events:

```text
PreToolUse
PermissionRequest
PostToolUse
PreCompact
PostCompact
SessionStart
SessionEnd
UserPromptSubmit
SubagentStart
SubagentStop
Stop
Interrupt
```

The capture-relevant native inputs have these shapes:

```text
UserPromptSubmit
  session_id
  turn_id
  cwd
  model
  permission_mode
  transcript_path: string | null
  prompt
  agent_id? / agent_type?

Stop
  session_id
  turn_id
  cwd
  model
  permission_mode
  transcript_path: string | null
  last_assistant_message: string | null
  stop_hook_active

PostToolUse
  session_id
  turn_id
  cwd
  model
  permission_mode
  transcript_path: string | null
  tool_name
  tool_input
  tool_response
  tool_use_id

SessionEnd
  session_id
  cwd
  transcript_path: string | null
  reason: "other"
```

`UserPromptSubmit`, `Stop`, and `PostToolUse` provide stable native session and
turn coordinates. `PostToolUse` also provides a native tool-use coordinate.
`SessionEnd` provides no turn coordinate.

No inspected hook input provides a source timestamp. Each local Codex
transcript record does provide a top-level timestamp and ordinal. Each record
also has a record type and payload. The transcript is therefore a separate,
richer native source. The hook payload only provides its nullable location.

## Evidence Boundary

The hook payload contract and the transcript record contract are distinct
provider facts. No current design may treat `transcript_path` as guaranteed
content or invent a source time from hook delivery.

One completed top-level Codex turn produces two independently accepted evidence
items:

```text
UserPromptSubmit -> one exact user-message evidence item
Stop             -> one exact assistant-message evidence item
```

The two items preserve their shared native `session_id` and `turn_id`. They do
not become one synthetic captured event. Session curation may interpret them
together later without changing their evidence identity.

For the controlled development fixture, `(session_id, turn_id,
hook_event_name)` identifies each expected observation. The future automatic
capture unit must establish its own durable delivery and replay behavior; this
unit does not claim that one hook invocation proves delivery.

The future adapter preserves the exact native hook JSON as source material and
leaves provider occurrence time absent. Hook receipt and durable acceptance
time remain separate application facts.

The development fixture must create one controlled equivalent of each
post-normalization event. One fixture invocation can submit the ordered pair,
but each observation proceeds through shared ingestion as a separate evidence
candidate.

Only the top-level conversation enters the first capture slice. Provider
internal prompts and `SubagentStart` or `SubagentStop` activity remain outside
this boundary.

## Evidence Basis

- Installed runtime: `codex-cli 0.153.0`.
- Installed feature report: `hooks` is stable and enabled.
- Embedded command-hook input schemas from that installed executable.
- Shape-only inspection of a local Codex JSONL transcript generated by the
  same installation.
- [Official Codex Hooks documentation](https://learn.chatgpt.com/docs/hooks).

These observations verify the installed local contract. They do not establish
compatibility with a future Codex version.

Automatic hook installation, reliable delivery, failure recovery, and
transcript reconciliation are deferred to Roadmap Step 7.
